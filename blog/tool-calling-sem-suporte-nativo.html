Tool calling em LLMs que não sabem chamar ferramentas

Um agente precisa de ferramentas. Quando o modelo não tem suporte nativo, dá para implementar o protocolo do lado de fora.

nov 2026 LLMsagentesPydantic

No EurecaChat, os agentes respondem perguntas sobre dados acadêmicos chamando ferramentas: funções Python que consultam APIs e fazem agregações em SQL. Com modelos que têm tool calling nativo, isso é quase de graça. O framework envia a lista de ferramentas, o modelo devolve uma chamada estruturada e o código executa.

Só que nem todo modelo open-source faz isso. Algumas versões de LLaMA e Qwen simplesmente não têm o recurso. Mesmo assim, a gente queria usá-las. Então implementamos o protocolo por fora.

A ideia

Tool calling é, no fundo, um contrato de formato:

  1. O modelo recebe a descrição das ferramentas disponíveis.
  2. Ele responde dizendo qual ferramenta quer e com quais argumentos.
  3. O código executa a ferramenta e devolve o resultado ao modelo.

O suporte nativo só garante o passo 2 com um formato confiável. Sem ele, quem garante o formato é o prompt, e o código valida.

1. Descrever as ferramentas no prompt

Cada ferramenta vira um bloco de texto com nome, descrição e parâmetros, e o prompt pede uma resposta em JSON, e só JSON:

# exemplo simplificado
SYSTEM = """Você tem acesso às ferramentas abaixo.
Para usar uma, responda APENAS com um JSON no formato:
{"tool": "<nome>", "args": {...}}
Quando já puder responder ao usuário, use:
{"tool": "final_answer", "args": {"text": "..."}}

Ferramentas:
""" + descrever_ferramentas(TOOLS)

2. Validar a saída antes de confiar nela

O modelo vai errar o formato de vez em quando: texto antes do JSON, aspas simples, um campo faltando. Por isso a resposta passa por um parser tolerante e depois por validação com Pydantic: 

from pydantic import BaseModel, ValidationError

class ToolCall(BaseModel):
    tool: str
    args: dict = {}

def parse_tool_call(raw: str) -> ToolCall:
    # pega o primeiro objeto JSON da resposta, ignorando texto em volta
    start, end = raw.find("{"), raw.rfind("}")
    return ToolCall.model_validate_json(raw[start:end + 1])

3. Despachar a função manualmente

Um dicionário liga o nome da ferramenta à função Python. Os argumentos também são validados, contra o schema da própria ferramenta:

TOOLS = {"disciplinas_do_curso": disciplinas_do_curso, ...}

def dispatch(call: ToolCall):
    if call.tool not in TOOLS:
        return f"Ferramenta '{call.tool}' não existe. Opções: {list(TOOLS)}"
    return TOOLS[call.tool](**call.args)

O resultado volta para o histórico como uma nova mensagem, e o loop continua até o modelo chamar final_answer.

O que dá errado (e como contornar)

  • JSON quebrado: em vez de falhar, devolva o erro de validação ao modelo e peça a correção. Na maioria das vezes ele corrige na tentativa seguinte. Coloque um limite de tentativas.
  • Ferramenta inventada: o modelo chama algo que não existe. A mensagem de erro deve listar as opções válidas, como no dispatch acima.
  • Loop infinito: o modelo chama a mesma ferramenta com os mesmos argumentos repetidamente. Limite o número de passos e detecte chamadas repetidas.
  • Resultado grande demais: ferramentas que devolvem milhares de linhas estouram o contexto. É por isso que, no EurecaChat, as ferramentas devolvem dados já agregados em SQL.

A lição: tool calling nativo é conveniente, mas não é mágico. Com um formato claro, validação forte e boas mensagens de erro, modelos menores e abertos conseguem trabalhar como agentes.
